# ЛР4 CYBERcobra — вариант 12

Учебный процессор `CYBERcobra 3000 Pro 2.1` собран из блоков ЛР1–ЛР3.
Программа варианта 12 формирует число из чётных двоичных разрядов входа:
`result[k] = input[2*k]`, нумерация разрядов начинается с нуля.
Для `SW=0x03B8` результат — **20 (`0x14`)**. Основная программа приходит к
**`PC=0x2C` после 35 обычных фронтов после сброса** и остаётся в `J 0`.

Для защиты начните с [наглядного сеанса Vivado](walkthrough/README.md): исходники,
поведенческая симуляция и волны, затем RTL-схема; сборка для платы идёт после них.

## Что нужно знать сначала

**Бит** — одна цифра двоичной записи: `0` или `1`.
HEX-запись `03B8` соответствует двоичной `0000 0011 1011 1000`: каждая
шестнадцатеричная цифра задаёт четыре двоичные цифры.

**Регистр** — небольшая ячейка памяти внутри процессора. В этой лабораторной каждый
регистр хранит 32 бита. В ней хранится число, которое команда может прочитать или
заменить. Например, при `r1=5` и `r2=3`
команда `r3 = r1 + r2` запишет в `r3` число `8`. Набор таких регистров называется
регистровым файлом.

**PC (program counter, счётчик команд)** — отдельный регистр с байтовым адресом
текущей команды в ROM. Каждая команда занимает 32 бита, то есть 4 байта, поэтому
обычные последовательные адреса — `0, 4, 8, 12, …` (здесь десятичные числа).
При переходе PC получает другой адрес. Это адрес команды, а не число выполненных шагов.

**Однотактное устройство** исполняет одну команду за один период такта в обычном
режиме. Период — интервал между соседними переходами тактового сигнала `0→1`
(положительными фронтами), а не между любыми двумя переключениями `0/1`.
Между положительными фронтами комбинационная логика читает команду и
регистры, вычисляет результат и следующий PC. На следующем положительном фронте
PC и разрешённая запись в регистр фиксируют результат этой команды.
Вся программа занимает много тактов: для `03B8` она получает результат и приходит
к конечному `J 0` за **35 обычных тактов после сброса**.

**`03B8 → 14` — обе записи шестнадцатеричные (HEX)**: `0x03B8 = 952` в десятичной
системе, а `0x14 = 20`. Программа выбирает чётные биты исходного числа и упаковывает
их подряд. Она не переводит одно и то же число из шестнадцатеричной системы в десятичную.
Вход `0000001110111000` в двоичном виде имеет единицы в разрядах `3, 4, 5, 7, 8, 9`
(считаем справа с нуля). Из них чётные — `4` и `8`; они переходят в разряды результата
`2` и `4`, поэтому получается `4 + 16 = 20`, то есть HEX `14`.
Короткий пример: двоичное `0110₂` (6), номера разрядов слева направо — `3, 2, 1, 0`.
Берём чётные разряды `2` и `0`: их значения — `1` и `0`, результат — `10₂` (2).
Выбранный нулевой бит тоже сохраняет своё место в результате.

## Как работает программа

Из входа берётся младший бит, переносится в очередной разряд результата, а вход
сдвигается вправо на два бита. Цикл заканчивается, когда оставшийся вход равен нулю.
`r1` хранит результат, `r2` — оставшийся вход, `r3=1`, `r4` — позицию результата,
`r5=2`, `r6` — выбранный бит.

```text
r2 = IN; r1 = 0; r3 = 1; r4 = 0; r5 = 2;
do {
    r6 = (r2 & r3) << r4;
    r1 = r1 | r6;
    r2 = r2 >> r5;
    r4 = r4 + r3;
} while (r2 != 0);
J 0;  // RA1 = r1: результат виден на out_o
```

Основной `program.mem` обрабатывает **32-битный операнд после знакового расширения
`sw_i` 16→32**: `{{16{sw_i[15]}}, sw_i}`. Поэтому `03B8→14`, `8000→FF00`,
`FFFF→FFFF`. Отдельный `program_low16.mem` сначала оставляет только физические
16 бит (`AND 65535`): `03B8→14`, `8000→00`, `FFFF→FF`.
Текст варианта не уточняет этот крайний случай; на защите назовите выбранный
контракт. В обоих режимах используется одно и то же ядро.

## От простой схемы к сигналам

PC выбирает команду из ПЗУ. Команда задаёт, какие регистры прочитать, что сделать
с их значениями в АЛУ и куда записать результат. На каждом положительном фронте
обновляются PC и, если запись разрешена, один регистр.

Путь данных: **PC → ROM инструкций → регистровый файл → АЛУ → мультиплексор
записи → регистровый файл**. Поля команды управляют этим путём. Обратная связь PC:
**PC → сумматор → следующий PC → PC**; мультиплексор выбирает `+4` или знаковое
смещение перехода, умноженное на 4.

- ROM: **512 байт, 128 слов по 32 бита**, асинхронное чтение по `pc[8:2]`.
  `PC` — байтовый адрес, поэтому следующая обычная команда находится через 4 байта.
- Регистровый файл: **32×32**, два асинхронных порта чтения и один синхронный порт
  записи. Регистр `r0` читается как ноль, запись в него запрещена.
- `RA1/RA2/WA` — адреса регистров; `rd1/rd2/write_data` — сами 32-битные значения.
- `WS`: `00` — знакорасширенная 23-битная константа, `01` — АЛУ,
  `10` — вход после SE16→32, `11` — ноль.
- `we = ~(J | B)`: команды перехода не записывают регистры.
  Переход выбирается при `J | (B & alu_flag)`.
- **Отдельной памяти данных с load/store в ЛР4 нет.** Данные хранятся в регистрах.
- **`out_o = rd1`**, а не постоянно `r1`. Во время цикла выход меняется вместе с
  `RA1`; конечная команда `J 0` читает `r1` и удерживает результат на выходе.

Сброс **синхронный, активный HIGH**: PC становится нулём только на положительном
фронте при `rst_i=1`. У регистрового файла нет входа reset; программа сама задаёт
нужные начальные значения. Сброс PC не очищает RF и не блокирует его запись.

На фронте исполняется команда, видимая **до фронта**. После обновления PC на волне
уже видны поля следующей команды. Поэтому сопоставляйте запись в RF с прежней
командой, а новое значение PC — со следующим адресом. До инициализации регистров
значения `X` в симуляции возможны.

## Полная самопроверка отдельно от GUI

В терминале, из `Lab4_CYBERcobra`, с доступной командой Vivado:

```bash
python3 -m unittest discover -s tests -p 'test_*.py'
vivado -mode batch -nojournal -nolog -source build_sim.tcl -tclargs default directed
vivado -mode batch -nojournal -nolog -source build_sim.tcl -tclargs default exhaustive
vivado -mode batch -nojournal -nolog -source build_sim.tcl -tclargs low16 exhaustive
```

**Не выполняйте `source build_sim.tcl` в GUI**: это batch-сценарий, который
отказывается работать при открытом проекте и закрывает созданный им проект по
окончании. Он создаёт отдельный `build/sim_…`, не заменяет исходный `program.mem` и
печатает `LAB4_SELF_CHECK=PASS` только при `test_pass=1`. Directed — 9 примеров;
exhaustive — все 65 536 значений SW и 9 дополнительных примеров.

Программа занимает 12/128 слов ROM (low16 — 14/128). Предупреждение `$readmemh` о
коротком образе ожидаемо; конечный self-loop не даёт исполнить незаданные слова.
Остановки `FATAL`, `ERROR`, watchdog и `test_pass=0` не считаются успехом.

## Статус проверки

Ранее, 10 ноября 2026 года, для этих RTL и образов записаны успешные полные прогоны
Icarus Verilog и **Vivado/XSim 2023.1**: в каждом режиме 65 545 запусков программы,
196 659 проверок, `test_pass=1`, `LAB4_SELF_CHECK=PASS`. Конвертер прошёл 8 тестов.
Это результаты подготовленного комплекта; новый checkout и GUI-сеанс не выдаются
за повторный полный прогон XSim. Демонстрационный `tb_lab4_demo` локально прошёл
**43 проверки в Icarus**; фактический сеанс с GUI-помощниками пока не проверен.

Ранее собран default32-битстрим: 820/820 сетей трассированы, routing errors — 0.
Для ограниченного системного такта 100 МГц: WNS +6.222 ns, WHS +0.140 ns.
Остались 94 `no_clock` и 432 unconstrained internal endpoints; ручной такт CPU
не ограничен, полная timing-валидация CPU не установлена. В routed DRC — 0 errors,
0 critical warnings и одно `CFGBVS-1` из-за незаданных `CFGBVS/CONFIG_VOLTAGE`;
предупреждение не подавлялось. Это не подтверждает полную электрическую проверку.
**Физическая плата и JTAG не проверялись.** Битстрим и серверные логи в этот
репозиторий не включены.

## Позже: Nexys A7-100T

Чип **`xc7a100tcsg324-1`**, аппаратный top **`nexys_CYBERcobra`**.
В GUI после разбора схемы: **Run Synthesis → Run Implementation → Generate Bitstream**.
Либо в отдельном терминале из Lab4:

```bash
vivado -mode batch -nojournal -nolog -source build_bitstream.tcl -tclargs default
```

Проверьте полный timing/DRC. На ПК с физически подключённой по USB платой:
**Open Hardware Manager → Open Target → Auto Connect → Program Device** и свой `.bit`.
Удалённый рабочий стол сам по себе не передаёт локальный USB/JTAG.
SW задают вход до IN, BTND даёт такт; для сброса удерживайте CPU_RESET и нажмите
BTND, затем отпустите reset. Для `03B8` после сброса нужны 35 обычных нажатий:
`PC=2C`, LED=`0014`. На конечном `J 0` новый вход не читается до нового запуска.
